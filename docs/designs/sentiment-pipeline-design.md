## Problem Statement
Analisis sentimen komentar sosmed saat ini dilakukan manual (baca satu-satu / spreadsheet), tidak bisa diskalakan untuk ribuan komentar per batch. Data contoh yang sudah ada: 6.158 komentar+balasan dari 200 video TikTok. Kebutuhannya bukan cuma persentase positif/negatif, tapi juga menangkap *messaging* — topik/kata yang paling sering muncul di komentar, karena itu yang menunjukkan perhatian audiens sebenarnya.

## Demand Evidence
Data nyata sudah ada dan sudah dianalisis sebagian secara manual — ditemukan 3 akun brand/admin (`dokterrizkimrd`, `yayleindonesia`, `yaylesupport`) yang mendominasi balasan dan perlu dikecualikan dari analisis. Ini bukan proyek hipotetis: PRD dibawa sudah lengkap dengan draf keputusan arsitektur (ADR-01 s.d. ADR-04), skema data, dan aturan kerja — hasil dari diskusi user tanggal 30 Agustus 2026 sebelum sesi ini dimulai.

## Status Quo
Baca manual satu-satu atau spreadsheet. Tidak mungkin diskalakan untuk 6.158 komentar per batch, apalagi kalau volume bertambah.

## Target User & Narrowest Wedge
**Target:** Analis internal (operator CLI) — satu orang, jalan lokal, tidak ada konsep login/multi-role. Ini asumsi terkunci untuk v1 (bukan keputusan terbuka) — lihat Open Questions untuk syarat kapan asumsi ini perlu direvisi.
**Wedge tersempit (rilis ini):** dua CLI Python terpisah (analisis sentimen + generate laporan HTML), TikTok-only, tanpa histori/DB, tanpa pipeline terjadwal, tanpa web UI. Platform lain (IG/X/YouTube) & deteksi otomatis akun internal sengaja ditunda. **Catatan scope:** "arsitektur disiapkan lewat pola adapter" berarti `ingest.tiktok_adapter` menerapkan interface `ingest.base` yang cukup jelas untuk platform lain mengikuti pola yang sama nanti — bukan alasan untuk menulis adapter kosong/interface generik ekstra sekarang. Tidak ada adapter platform lain dibangun di rilis ini, titik.

## Constraints
- Bahasa Indonesia (termasuk slang TikTok) — bukan multibahasa.
- Biaya LLM harus terkendali: eskalasi hanya untuk komentar ambigu, bukan seluruh data (hybrid lexicon+LLM, ADR-02).
- Laporan HTML harus bisa dibuka offline tanpa server, tanpa koneksi internet wajib.
- Kegagalan satu komentar (parsing/LLM) tidak boleh menghentikan seluruh run.
- Kredensial LLM hanya lewat env var, tidak pernah di file yang di-commit.
- Urutan preprocessing (`case_folding → cleaning → normalizing → tokenizing → filtering → stemming`) sudah disepakati, tidak boleh diubah tanpa diskusi ulang.
- Kata negasi (`tidak`, `bukan`, `belum`, `jangan`) tidak boleh masuk stopword — krusial untuk akurasi sentimen.
- Belum ada angka hard-limit biaya/waktu (mis. "$Y per run", "X menit untuk 6.158 komentar") karena tarif router LLM belum ditentukan (lihat Open Questions) — kontrolnya adalah proses: FR-09 dry-run wajib dijalankan dan direview manual SEBELUM run produksi penuh pertama, bukan angka tetap yang dipatok sekarang.

## Premises
1. **Masalah nyata & arsitektur 2-CLI-lewat-JSON tepat untuk skala ini** (single analyst, one-off per file — server/DB cuma nambah biaya perawatan tanpa manfaat). — Setuju.
2. **Hybrid lexicon+LLM (bukan lexicon murni atau LLM murni) adalah keputusan yang benar** — lexicon murni coverage rendah untuk slang TikTok, LLM murni mahal untuk ribuan komentar. Threshold eskalasi (skor -0.15..0.15, OOV >50%) belum dikalibrasi ke data nyata — limitasi eksplisit yang sudah dicatat di PRD. — Setuju.
3. **LLM provider diubah dari Anthropic-spesifik jadi provider-agnostic via client OpenAI-compatible** (`base_url` configurable) — user akses LLM lewat router pihak ketiga (bukan Anthropic langsung), env kosong (`LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`) untuk diisi user sendiri. Kontrak prompt tidak berubah. — Setuju, provider-agnostic.
   - **Dampak dokumen:** `Architecture.md` dan `Schema.md` di `docs/` diupdate ke v0.2 mengikuti keputusan ini.
4. **ADR-03 direvisi:** exclude-list manual tetap untuk akun pola-perilaku (mis. staff/support yang bukan pengunggah video), TAPI ditambah auto-exclude khusus akun pengunggah video (FR-11) — karena identitas pengunggah video diketahui pasti dari metadata video, bukan ditebak dari pola perilaku, jadi tidak ada risiko false-positive yang bikin ADR-03 asli menolak deteksi otomatis. — Setuju.
   - **Blocker teknis ditemukan & dikonfirmasi ke user (sesi office-hours):** dicek langsung ke data asli (`runs/2026-08/comments.json`) dan kode scraper (`tiktokcomment/tiktokcomment.py`) — `video_url` di data nyata adalah share-tracking link, BUKAN format `@username/video/id`, dan scraper cuma manggil endpoint `comment/list/` yang tidak pernah mengembalikan info uploader. Field `video_author_username` **tidak ada** di data yang dikumpulkan sekarang.
   - **Keputusan AWAL (office-hours, SUDAH DIREVISI — lihat catatan di bawah):** user awalnya pilih tambah panggilan API baru di scraper (endpoint video-detail).
   - **SUPERSEDED di sesi /plan-eng-review berikutnya:** opsi API-call ditolak (dobelin request volume ke TikTok per video, naikin resiko block — lihat Issue 3 di eng-review). User lalu mengusulkan solusi lebih baik: kolom CSV input baru (`nama_pengguna_kreator`, ditambah ke `id_konten,account_type` yang sudah ada di order-mirror analis), dibaca `tiktokcomment/runner.py`. **Zero API call tambahan, zero resiko block.** Ini keputusan FINAL — `PRD.md` v0.4, `Architecture.md` v0.4, `Schema.md` v0.4 semua reflect CSV-column approach ini, BUKAN API-call. Baca dokumen-dokumen itu (versi terbaru), bukan bagian office-hours ini, untuk detail implementasi FR-11.
   - **Dampak dokumen:** `PRD.md` (FR-11 + kriteria penerimaan), `Architecture.md` (ADR-03 revisi 2x — API-call lalu CSV-column), `Schema.md` (field baru `video_author_username`, enum `exclude_reason` baru, sumber diklarifikasi CSV bukan API) — semua di v0.4.

## Approaches Considered

### Approach A: Sequential ketat sesuai Fase PRD
Selesaikan Modul Analisis 100% (termasuk LLM hybrid penuh) baru mulai Modul Laporan. Effort: M. Risk: Med. Tidak ada output yang bisa dilihat analis sampai modul 1 selesai penuh — kalau ada asumsi schema meleset, ketauannya telat.

### Approach B: Vertical slice tipis dulu (DIPILIH)
Bangun pipeline end-to-end versi tipis dulu: ingest→flatten→lexicon-only (skip LLM)→TF-IDF sederhana→JSON→HTML minimal, jalan di data asli (6.158 komentar) secepat mungkin. Baru lapis eskalasi LLM, exclude-list transparency (FR-10), dry-run (FR-09) di atasnya. Effort: M. Risk: Low.

**Definisi "selesai" untuk slice tahap 1** (batas I/O, bukan detail implementasi — lihat `Schema.md` v0.2 untuk field lengkap):
- Input: `comments.json` asli (6.158 entri).
- Output: `analysis_result.json` sesuai skema penuh di `Schema.md` §4, TAPI `sentiment_method` selalu `"lexicon"` (belum ada nilai `"llm"`/`"llm_failed"` di tahap ini — itu ditambah di lapis berikutnya).
- Output: `report.html` minimal — menampilkan `meta`, `sentiment_summary`, `top_keywords_overall`, distribusi sentimen. Section yang butuh data LLM (kalau ada) boleh kosong/placeholder di tahap ini.
- Selesai kalau: analis bisa buka `report.html` dan baca hasil analisis lexicon-only dari data asli, tanpa error, tanpa panggilan API LLM sama sekali.

### Approach C: Paralel begitu Schema dikunci
Sesuai PRD §11 — begitu `Schema.md` disepakati, Modul 1 & 2 dikerjakan bersamaan (Modul 2 pakai fixture JSON manual). Effort: M-L. Risk: Med (butuh disiplin sync schema, perlu fixture ekstra).

## Recommended Approach
**Approach B — Vertical slice tipis dulu.** Alasan: `Schema.md` (kontrak `analysis_result.json`) adalah bagian paling kritis yang harus dijaga stabil — validasi lebih cepat kalau seluruh chain (ingest→...→report) jalan di data asli sedini mungkin, sebelum menulis logika LLM hybrid yang lebih mahal untuk diubah kalau ternyata skema perlu revisi. Threshold ambigu (0.15 / OOV 50%) juga butuh dikalibrasi terhadap data nyata — makin cepat report bisa dibaca analis, makin cepat kalibrasi itu terjadi.

## Open Questions
(Diwariskan dari asumsi eksplisit di `PRD.md` §9 dan `DESIGN.md` — belum dijawab, bukan bagian dari sesi ini)
- Definisi "ambigu" untuk eskalasi LLM (threshold skor, rasio OOV) belum dikalibrasi ke data nyata — wajib direview manual setelah run pertama.
- Exclude-list awal (`dokterrizkimrd`, `yayleindonesia`, `yaylesupport`) perlu dikonfirmasi apakah lengkap — ada akun internal lain yang mungkin terlewat?
- Asumsi single-user (di atas) terkunci untuk v1 — hanya perlu direvisi kalau ternyata sistem ini dipakai bergantian oleh lebih dari satu analis dengan hak akses berbeda (belum ada indikasi ini terjadi).
- Username di kartu contoh komentar disamarkan sebagian by default — perlu dikonfirmasi apakah analis butuh username utuh untuk tindak lanjut.
- Nilai `LLM_BASE_URL` dan `LLM_MODEL` router yang akan dipakai belum ditentukan — env dikosongkan sengaja untuk diisi user sebelum run pertama.
- Proses kalibrasi threshold ambigu belum ditentukan formatnya: berapa sampel komentar yang direview manual setelah run pertama, dan siapa yang menentukan threshold final? Perlu diputuskan analis sebelum run produksi pertama, bukan bagian dari sesi ini.
- Kalau rasio eskalasi LLM ternyata jauh lebih tinggi dari perkiraan (melanggar constraint biaya di atas), respons defaultnya adalah **kalibrasi ulang threshold** (bukan membangun fallback/circuit-breaker otomatis) — sesuai FR-09 dry-run yang memang dirancang untuk mendeteksi ini sebelum run sungguhan.

## Success Criteria
- G-01: 100% komentar (non-internal) di satu file input terklasifikasi tanpa intervensi manual per komentar.
- G-02: Top-20 keyword bisa ditelusuri balik ke komentar asli yang relevan (lolos spot check analis).
- G-03: Laporan HTML dibuka langsung dari filesystem tanpa server, tanpa koneksi internet wajib.
- G-04: Rasio eskalasi LLM tercatat per run, tidak menyasar seluruh data.
- G-05: Laporan HTML **selalu** menampilkan Blok Metodologi & Limitasi (metode hybrid, rasio eskalasi, limitasi reply-pertanyaan) — laporan tanpa blok ini dianggap gagal kriteria penerimaan FR-07, bukan opsional kosmetik.
- G-06: Sebelum run produksi pertama dianggap final, analis sudah menjalankan dry-run/run awal terhadap dataset penuh dan mengecek `excluded_accounts_detected` (FR-10) — akun top-N berdasarkan volume dikonfirmasi manual, bukan diasumsikan exclude-list awal (3 akun) sudah lengkap.

## Edge Cases
Divalidasi/ditangani oleh aturan yang sudah ada di `Schema.md` §2 dan `Rules.md` §2/§7 — dicatat di sini supaya terlihat eksplisit di ringkasan desain:
- Komentar dengan `comment` kosong (`""`) — field wajib ada tapi boleh kosong (`Schema.md` §2); ikut diproses seperti biasa, kemungkinan jatuh ke netral.
- Emoji-only comment (tanpa teks) — ditangani tahap `preprocessing/emoji.py` (ekstraksi emoji berjalan sebelum cleaning); token hasil stemming bisa kosong, tidak boleh membuat run gagal (per-komentar try/except, lihat `Rules.md` §6).
- `aweme_id`/`comment_id` tidak sesuai skema — ingest berhenti dengan exit code 2, menyebutkan ID yang bermasalah (`Schema.md` §2, `PRD.md` FR-01 kriteria gagal). Ini kegagalan yang MEMANG harus menghentikan run (beda dengan kegagalan LLM per-komentar).
- Reply bertingkat lebih dari satu level — di luar skema yang didokumentasikan (`replies[]` tidak boleh bertingkat lagi per `Schema.md` §2); kalau data nyata ternyata punya ini, ingest harus menganggapnya sebagai penyimpangan skema (exit code 2), bukan diam-diam di-flatten lebih dalam. **Action sebelum implementasi ingest:** cek kedalaman nesting di `comments.json` asli (6.158 entri) — kalau ternyata ada reply bertingkat >1 level di data nyata, keputusan hard-fail ini harus dikonfirmasi ulang ke user sebelum dikunci, bukan diasumsikan aman.
- Duplikat `comment_id` antar video — tidak eksplisit disebut di `Schema.md`; kalau muncul di data nyata, catat sebagai temuan saat implementasi (bukan diasumsikan tidak akan terjadi).

## Distribution Plan
Tidak relevan — CLI internal, satu analis, dijalankan lokal (`pip install -e .` dari `pyproject.toml` di venv lokal). Tidak ada rilis publik, package registry, atau deployment pipeline. Keputusan eksplisit sesuai PRD §5 (di luar cakupan rilis ini).

## Dependencies
- File input `comments.json` (format hasil scraping TikTok, struktur `video→comments[]→replies[]`).
- Lexicon sentimen Indonesia (InSet atau setara) + PySastrawi untuk stemming.
- Akses LLM API via router OpenAI-compatible — `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL` (env kosong, diisi user).
- `config/exclude_accounts.yaml` (minimal 3 kandidat awal) dan `config/stopwords_custom.txt`.
- **Blocker untuk FR-11:** scraper (`tiktok-comment-scrapper/tiktokcomment/tiktokcomment.py`) belum punya field `video_author_username` — perlu ditambah panggilan API video-detail per video dulu (repo yang sama, kerja terpisah dari 2 modul pipeline sentimen). Sampai field ini ada, FR-11 di-skip secara aman (fallback ke exclude-list manual, lihat kriteria gagal FR-11 di `PRD.md`).

## The Assignment
Dua hal konkret sebelum baris kode pertama ditulis:
1. Isi `LLM_BASE_URL` dan `LLM_MODEL` (nama router & model yang mau dipakai) supaya kontrak `meta.config_used.llm_base_url` di `Schema.md` bisa diverifikasi dengan satu panggilan API non-mutating begitu `llm_classifier.py` ada.
2. Putuskan urutan: kerjakan tambahan API video-detail di scraper (FR-11 blocker) DULU sebelum mulai vertical slice sentimen, atau paralel — karena FR-11 cuma prioritas "Sebaiknya" (bukan "Wajib"), vertical slice (Approach B) tetap bisa jalan tanpa field ini (fallback ke exclude-list manual), tapi keputusan urutan ini sebaiknya eksplisit sebelum kerja dimulai, bukan diasumsikan.
