## Problem Statement
The `/autoplan` review of the "close the 3 open items" plan (InSet lexicon + FR-09
dry-run + threshold calibration) surfaced a proven correctness bug: `score_tokens()`
preserves negation tokens through preprocessing but never consumes them, so
`tidak bagus` scores positif at confidence 1.0. Swapping in the InSet lexicon (9,074
words vs the 28-word starter) would make this bug fire on real data instead of staying
dormant. Eng review found `tidak` itself carries weight -5 in InSet, so even a naive
sign-flip fix still mislabels `tidak kecewa`. Fixing this properly inside the lexicon
architecture means ~6 interacting semantic decisions (operator-vs-scored negation,
OOV redefinition, confidence rescaling, dual-key raw/stemmed lookup, escalation-band
split) — costed at 26 P1 tasks in the eng review.

Separately, the CEO review priced the "LLM is too expensive" premise behind ADR-02
and found it false at this scale: ~$0.13-$2.90 per monthly run. And it found a
pretrained Indonesian sentiment classifier was never evaluated as an alternative to
building/fixing the lexicon at all.

## Demand Evidence
Real production blocker, not hypothetical: the plan to ship InSet was already reviewed,
tasked, and about to be built when the negation bug was found. The user has an existing
LLM router account (mixed free/paid keys, already used elsewhere) and confirmed it can
round-robin models — UC1 is not a new dependency, it already exists.

## Status Quo
`sosmed_sentiment/sentiment/lexicon_classifier.py` ships a 28-word starter lexicon.
Almost every comment misses it and lands "netral" by default — not because the
comments are neutral, but because the lexicon is empty. This is the state the 3-item
plan was meant to fix.

## Premises
1. **The existing lexicon→LLM escalation architecture (cheap pass first, expensive
   pass only for uncertain cases) is sound and should be reused, not rebuilt.** —
   User agreed explicitly (Premise 3 from this session).
2. Cheap-and-fast should run before expensive-and-slow, not after — reverses the
   user's original "UC1 until maxed, then UC2" framing. — Not contested.
3. A 50/50 split of comments between the local model and the LLM (the user's initial
   idea) wastes both: easy comments would sometimes land on the paid LLM, hard
   comments would sometimes land on the free-but-weaker layer. Routing should be by
   per-comment difficulty (model's own confidence), not by an arbitrary split. —
   Not contested; superseded by Approach C below (single free layer, no split needed).

## Approaches Considered

### Approach A: Local model replaces the lexicon at the cascade's first position
Model outputs its own confidence in place of the lexicon's OOV ratio; low confidence
escalates to the LLM via the existing `is_ambiguous()` gate. Starter lexicon kept as
an offline fallback if the model fails to load. Effort M, Risk Low.

### Approach B: Three-layer cascade — lexicon, then model, then LLM
Keeps every piece of lexicon work already reviewed (negation fix, dual-key lookup),
adds the model as a second free filter before the LLM. Maximizes LLM-call savings.
Effort L, Risk Med — three systems to maintain and debug when a label looks wrong.
Rejected: the LLM call it's optimizing away already costs $0.13-$2.90/month total: not
worth a third system's maintenance burden.

### Approach C: Local model replaces the lexicon entirely — CHOSEN
Delete the InSet-lexicon plan (negation fix, dual-key lookup, confidence rescaling —
the bulk of the 26 P1 eng-review tasks). The pretrained model becomes the sole free
layer; a model trained on Indonesian social text is expected to generalize past
negation and informal slang better than a hand-built lexicon, but this is not yet
verified against this repo's actual data — see Feasibility Note below.
LLM escalation on low model-confidence. **Not** a drop-in to `is_ambiguous()`'s
current shape — see Feasibility Note.
Effort S, Risk Low.

**Feasibility note (added after adversarial review):**
- `hybrid.is_ambiguous(score, oov_ratio, ...)` (`sosmed_sentiment/sentiment/hybrid.py:16-23`)
  takes two independent signals — a signed score (positive/negative direction +
  magnitude) and an OOV ratio (how much of the text the lexicon didn't recognize) —
  combined with OR. A classifier model instead returns a label
  (`positif`/`negatif`/`netral`) plus one confidence value. There is no OOV-ratio
  equivalent — the model always "recognizes" the text, it just may be unsure. This
  means `is_ambiguous()`'s signature and body change (single confidence threshold,
  not two independent thresholds); "same shape as today" in an earlier draft of this
  doc overstated the compatibility. Rewrite scope is small (one function), but it is
  real work, not zero work.
- `tidak bagus` / `tidak kecewa` handling by the pretrained model is an **assertion
  from the model's training description, not yet tested against this repo's data**.
  Verify with a direct probe (run both negation test cases through the model) before
  relying on it — same discipline this session already applied to the InSet stemming
  claim and the LLM cost claim, both of which turned out to need direct measurement
  rather than trusting the written description.
- Inference throughput/latency for a monthly batch (6,000-10,000 comments) on the
  analyst's CPU (no GPU assumed — none was mentioned as available) is not yet
  estimated. Get one real timing number before committing, the way the Sastrawi
  stemming bottleneck was measured directly earlier in this project rather than
  assumed.
- **Rejection criterion (was missing):** if the model's measured accuracy against the
  Tahap B labeled sample falls below the target set in Open Questions, Approach C is
  rejected and Approach A (model + lexicon fallback layer) or a return to the
  InSet-lexicon plan is reconsidered — this decision is not final until that
  measurement exists.

## Recommended Approach
**Approach C.** The user already agreed the cascade shape stays (Premise 1). Given
that, the choice is what fills the cheap layer — and a model trained on Indonesian
social text handles the exact failure class (negation) that forced this whole
re-review, without a hand-rolled fix. Approach B's extra savings target an LLM call
that's already priced under $3/month; that's optimizing a cost that isn't the
bottleneck. User selected C directly via AskUserQuestion.

## Open Questions
- **Accuracy target (was UC3).** The model's own confidence score is not the same as
  correctness — a model can be confidently wrong. No accuracy target exists in any of
  the 5 project docs. Confidence *can* replace the lexicon's OOV-ratio as the
  escalation signal (that part is answered), but "how accurate is this pipeline" still
  needs the human-labeled sample that Item 3 (Tahap B) already planned — this
  revision doesn't remove that step, it just changes what's being measured against.
- Exact confidence threshold for escalation — needs calibration against the same
  labeled sample, same as the lexicon threshold would have. No default assumed yet;
  do not hardcode a starting value (e.g. 0.7) without running it against real
  comments first — this project has twice found written assumptions wrong when
  finally measured (Sastrawi cache claim, LLM cost claim).
- Whether `torch`+`transformers` (~475 MB model + library weight) is acceptable
  given the repo's "stay light" convention — not re-litigated this session, flagged
  for the next review pass.
- Multi-word/typo InSet lexicon problems (740 multi-word entries, 1,142 pos/neg
  duplicates) — moot under Approach C; noted so nobody re-derives them later.

## Reviewer Concerns
- Adversarial review (2nd pass) flagged the absence of a provisional/default
  confidence threshold as unfixed. This is deliberate, not an oversight: writing a
  placeholder number (e.g. "start at 0.7") risks it getting copy-pasted into code
  unchanged before calibration happens — precisely the failure mode this project
  already hit twice (an assumed Sastrawi cache that didn't exist, an assumed "LLM is
  expensive" premise that was never priced). No default is given until one is
  measured. Convergence guard applied — not looping further on this point.
