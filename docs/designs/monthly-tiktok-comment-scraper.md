## Problem Statement

Kantor meminta sistem untuk menarik komentar dari video TikTok milik brand sendiri setiap bulan. Data mentah komentar ini dipakai tim untuk menentukan arah campaign berikutnya dan key message brand — bukan oleh sistem ini sendiri (analisis sentimen/modelling dilakukan terpisah oleh tim, di luar scope proyek ini).

Repo yang dipakai adalah fork proyek open-source `tiktok-comment-scrapper` milik orang lain. Sebelum sesi ini, belum pernah dijalankan atau diverifikasi — statusnya "mungkin jalan, mungkin tidak, ada bug atau tidak, tidak diketahui."

## Demand Evidence

- "ada yg minta dan ini urgent. Karena ini nentuin campaign dari brand kita sendiri kedepannya" — permintaan datang dari kantor, terkait langsung ke arah campaign dan key message brand.
- Scope dikonfirmasi eksplisit: sistem ini hanya perlu mengambil **raw data komentar**; modelling/analisis sentimen dilakukan pengguna sendiri di luar sistem ini.

## Status Quo

- "ada sih, iya bener tapi manual dan perlu banyak effort" — saat ini komentar dikumpulkan dengan cara manual (scroll TikTok, catat sendiri), effort tinggi. Otomasi sekecil apapun sudah jadi lompatan besar dibanding kondisi sekarang.

## Target User & Narrowest Wedge

**PIC dikonfirmasi: user sendiri, sebagai data analis** — yang menjalankan tool ini tiap bulan. CLI terminal saja cukup, tidak perlu UI (mengunci Open Question operator-teknis di sesi sebelumnya — sudah benar, tidak perlu direvisi).

Dampak kalau data telat bukan ke satu jabatan spesifik, tapi ke **seluruh perusahaan**: brand jadi tidak tahu kondisi sentimen sosial yang sebenarnya, sehingga arah campaign/key message bisa salah ambil keputusan. Sehingga target output tetap:
1. Cukup terstruktur untuk diproses lanjut oleh data analyst (JSON + CSV, bukan cuma log).
2. Cukup jelas dibaca manusia untuk quick-check tanpa tooling tambahan.

Wedge tersempit: satu perintah yang mengambil komentar dari daftar video (multi-video, bukan satu-satu) dan menghasilkan satu dataset bulanan siap pakai — menggantikan proses scroll-catat manual.

## Constraints

- **Zero cost** — tidak boleh pakai TikTok API berbayar (Business/Ads API), tidak pakai proxy berbayar atau layanan captcha-solving berbayar.
- **Bulanan, berulang** — bukan skrip sekali pakai; harus bertahan dipakai ulang tiap bulan oleh orang yang mungkin bukan si pembuat kode.
- **Multi-stakeholder** — output dikonsumsi lebih dari satu peran (data analyst vs reviewer campaign), bukan cuma developer.
- **Skala besar** — sampai dengan **1000 video per bulan** dalam satu batch. Ini konstrain baru yang mengubah kalkulasi risiko rate-limit (lihat Recommended Approach) — jauh lebih berat dari asumsi awal "beberapa video".

## Premises

1. **Core scraping mekanisme terverifikasi jalan hari ini** — diuji langsung terhadap API publik TikTok (`https://www.tiktok.com/api/comment/list/`), tanpa header/token/proxy tambahan, berhasil menarik 32 komentar + 11 balasan dari satu video sample. Ini bukan asumsi, ini hasil test langsung.
2. **Kode saat ini punya bug fungsional nyata**, ditemukan lewat pengujian langsung, independen dari isu anti-bot:
   - `main.py` crash `TypeError` (bukan pesan error yang ramah) kalau `--aweme_id` tidak diisi — callback regex dijalankan terhadap `None`.
   - Flag `--size` yang didokumentasikan di README **tidak ada** di `main.py` — dijalankan langsung memunculkan `Error: No such option: --size`.
   - Regex `aweme_id` (`^\d+$`) hanya menerima ID angka murni, padahal README menyatakan bisa "url or id" — URL video TikTok akan silent-fail jadi `None`.
   - Field `caption` dan `video_url` di output JSON kosong. Penyebab pastinya diverifikasi saat implementasi: blok `share_info` sebenarnya MASIH ada di response, tapi kode lama hanya membacanya dari `comments[0]` — kalau komentar pertama kebetulan tidak membawa blok itu, caption ikut kosong. Perbaikannya membaca dari komentar mana pun yang punya `share_info`, dan menyusun `video_url` dari `aweme_id` sebagai cadangan yang selalu benar.
   - Tidak ada error handling — jika TikTok mengembalikan halaman block/captcha/rate-limit (bukan JSON), script crash tanpa retry.

   Tiga bug tambahan ditemukan saat implementasi Fase 1, tidak terlihat pada pengujian awal:
   - `Comment.json` memanggil `json.dumps(self.json)` — rekursi tak terbatas, properti itu tidak pernah bisa dipakai.
   - `Comment.__init__` memakai `replies=[]` sebagai default argument, sehingga satu list yang sama dibagi ke semua instance.
   - `get_all_comments` menjalankan `break` sebelum `extend`, jadi komentar halaman terakhir selalu terbuang, dan `has_more` halaman pertama tidak pernah diperiksa.
3. **Endpoint komentar adalah SATU-SATUNYA endpoint publik TikTok yang masih terbuka tanpa signing.** Diuji langsung pada 2026-08-28 dengan `requests` polos (tanpa cookie/token):

   | Endpoint | Hasil probe |
   |---|---|
   | `api/comment/list/` | HTTP 200, 16135 byte JSON asli — **jalan** |
   | `api/user/detail/` | HTTP 200, **0 byte** |
   | `api/post/item_list/` (daftar video akun) | HTTP 200, **0 byte** |
   | `api/search/general/full/` | HTTP 200, **0 byte** |
   | Halaman profil HTML `tiktok.com/@user` | HTTP 200, hanya 1485 byte — tanpa `SIGI_STATE`, `__UNIVERSAL_DATA_FOR_REHYDRATION__`, `secUid`, maupun `playCount` |

   Pola "HTTP 200 dengan body kosong" adalah tanda endpoint mewajibkan parameter signing (`msToken`/`X-Bogus`). Konsekuensi arsitektur: **penemuan video (discovery) tidak mungkin lewat `requests` polos, sedangkan pengambilan komentar tidak perlu browser.** Ini memisahkan sistem jadi dua jalur dengan karakteristik berbeda (lihat Recommended Approach).

4. **Ketergantungan pada API publik tidak resmi bersifat rapuh jangka panjang.** TikTok bisa mengubah struktur response atau menambah proteksi anti-bot kapan saja — ini sudah pernah terjadi (lihat bug caption/video_url di atas). Untuk kebutuhan bulanan berulang, ini risiko utama, bukan sekadar bug yang cukup ditambal sekali.
5. **Prioritas data adalah komentar, bukan kelengkapan metadata.** Dikonfirmasi user: "yg penting itu komentarnya". Angka 1000 video/bulan adalah batas atas, bukan target — isi nyata ditentukan CSV tiap bulan dan boleh jauh lebih sedikit.

## Approaches Considered

### Approach A: Minimal Patch
Perbaiki bug yang ditemukan di kode yang sudah ada tanpa mengubah arsitektur: sambungkan `--size` ke parameter size yang sebenarnya, perbaiki callback `aweme_id` agar tidak crash saat kosong, perluas parsing ID agar menerima URL TikTok, perbaiki path jmespath untuk `caption`/`video_url`, tambahkan try/except dasar dengan retry/backoff. Tetap CLI satu-video per eksekusi.
- Effort: S (human ~4 jam / CC ~15 menit)
- Risiko: Rendah
- Ditolak karena: tidak menjawab kebutuhan "bulanan, multi-video, multi-stakeholder" — bulan depan tetap harus dijalankan manual satu video per satu video.

### Approach B: Runner Bulanan Multi-Video
Semua perbaikan di Approach A, plus: input berupa daftar `aweme_id`/URL lewat file CSV (lihat Format Input Video di Recommended Approach) untuk banyak video sekaligus, output digabung jadi satu dataset per bulan (JSON + CSV) dengan label tipe akun sebagai kolom, structured logging, retry + backoff antar-request, dan mode "smoke test" (ambil 1 video, ukuran kecil) untuk memverifikasi API TikTok belum berubah sebelum menjalankan batch penuh.
- Effort: M (human ~1-2 hari / CC ~30-45 menit)

### Approach C: Tahan-Banting dengan Playwright
Semua yang ada di Approach B, ditambah lapisan browser asli (Playwright) yang membuka TikTok sebagai browser sungguhan untuk mengambil cookie/token terbaru secara otomatis sebelum request `requests` cepat dijalankan — mengantisipasi jika TikTok suatu saat menambah proteksi anti-bot yang membuat request polos gagal.
- Effort: L (human ~2-3 hari / CC ~1-1.5 jam)

## Recommended Approach

**Approach B + C digabung** (pilihan user), effort gabungan Fase 1-2: human ~3-4 hari / CC ~2-2.5 jam (lebih rendah dari jumlah mentah B+C karena setup project, model data, dan logging dipakai bareng oleh kedua fase, tidak dikerjakan dua kali). Fase 3 (discovery by username) menambah ~1-2 hari human / ~45 menit CC di atas itu. Dipecah jadi 3 fase implementasi, bukan dibangun sekaligus:

- **Fase 1 (SELESAI, 2026-08-28):** runner bulanan multi-video (B). Input CSV berisi URL/ID video, jalur `requests` polos tanpa browser. Terimplementasi di `batch.py` + `tiktokcomment/runner.py`; semua bug di Premis #2 diperbaiki dan diuji end-to-end terhadap video nyata — batch jalan, resume jalan, smoke test yang gagal terdeteksi dan menghentikan run, baris CSV rusak di-skip tanpa menggagalkan batch.
- **Fase 2 (dibangun bareng, tapi tidak aktif default):** lapisan Playwright (C), AKTIF sebagai fallback **sebelum batch dimulai** — dipicu oleh smoke test yang gagal (lihat definisi "gagal" di Decisions). C tidak dipicu di tengah batch yang sudah berjalan; kalau request individual gagal di tengah batch, itu ditangani retry/backoff biasa dari Fase 1, bukan oleh Playwright.
- **Fase 3 (fitur baru, ditambahkan setelah Fase 1 terbukti jalan):** discovery by username — lihat bagian di bawah.

### Arsitektur terbelah: browser untuk discovery, requests untuk komentar

Hasil probe (Premis #3) memaksa pembagian kerja yang justru menguntungkan:

| Jalur | Alat | Frekuensi | Alasan |
|---|---|---|---|
| Discovery (username → daftar video + metrik) | Playwright (browser asli) | Jarang — sekali per akun per bulan | Endpoint API-nya balikin 200 kosong tanpa signing; halaman profil polos cuma kerangka. Hanya browser yang menjalankan JS TikTok yang bisa membaca daftar video + view/engagement. |
| Pengambilan komentar | `requests` polos | Sangat sering — ribuan request per batch | Endpoint `comment/list` masih terbuka tanpa signing. Memaksa jalur ini lewat browser akan jauh lebih lambat dan berat tanpa manfaat apa pun. |

Ini keputusan sadar, bukan kompromi: browser dipakai hanya di tempat yang memang tidak ada jalan lain, dan tidak dipakai di jalur panas yang jumlah request-nya besar.

Rasionalisasi: demand terkonfirmasi bulanan dan lintas-stakeholder (cocok dengan B), sementara ketergantungan pada API tidak resmi adalah risiko nyata yang sudah pernah terjadi dalam proyek ini sendiri (bug caption/video_url) — sehingga lapisan pemulihan otomatis (C) langsung dibangun dari awal, bukan ditambah belakangan saat sudah terlanjur gagal di tengah siklus bulanan produksi. Pemisahan fase menjaga agar C tidak menambah beban di setiap run selama request polos masih berfungsi (murni fallback, bukan jalur default).

**Residual risk yang tidak dipecahkan oleh C:** Playwright hanya mengambil ulang cookie/session — kalau TikTok ke depannya mewajibkan parameter signing per-request (pola seperti X-Bogus/msToken), cookie saja tidak cukup dan C tidak otomatis menyelesaikannya. Ini risiko yang diterima, bukan risiko yang terpecahkan — kalau terjadi, perlu sesi office-hours ulang untuk desain ulang.

**Rate-limit dari satu mesin:** karena constraint zero-proxy, tidak ada mitigasi IP-based rate-limiting selain jeda antar-request (retry/backoff). Kalau kena rate-limit keras, fallback-nya manual: coba ulang beberapa jam kemudian. Ini risiko yang diterima sesuai batasan biaya, bukan sesuatu yang didesain untuk hilang total.

**Konsekuensi skala sampai 1000 video/bulan:** dengan cap 200 komentar/video (termasuk reply, reply per komentar dibatasi 10), satu batch penuh berarti puluhan ribu request individual (tiap halaman komentar + tiap komentar berbalasan = 1 request). Ini BUKAN sesuatu yang realistis dijalankan sekali duduk tanpa jeda dari satu mesin tanpa proxy — dua konsekuensi desain wajib:
1. **Batch harus resumable/checkpointed** — progres per baris CSV disimpan (video mana yang sudah selesai), supaya kalau run terhenti di tengah (rate-limit, listrik mati, dsb.) tidak perlu mulai dari video pertama lagi. Ini makin wajib mengingat estimasi durasi di bawah.
2. **Delay berlapis** (usulan user, diperluas) — lihat Kebijakan Delay.

### Kebijakan Delay (anti-deteksi bot)

Usulan user: jeda 7-10 detik setiap selesai satu video. Diterima, tapi **diperluas jadi dua lapis**, karena jeda antar-video saja tidak cukup: satu video dengan cap 200 komentar berarti beberapa request halaman komentar plus satu request per komentar yang punya balasan. Kalau hanya ada jeda antar-video, di dalam satu video sistem tetap menembak berkali-kali tanpa jeda — justru pola paling mudah dikenali sebagai bot.

| Lapis | Jeda | Alasan |
|---|---|---|
| Antar-video | 7-10 detik (acak dalam rentang, bukan angka tetap) | Usulan user. Diacak supaya tidak membentuk pola interval yang seragam. |
| Antar-request di dalam satu video (halaman komentar & balasan) | 1-3 detik (acak) | Menutup celah burst di dalam satu video, yang jumlah request-nya justru paling banyak. |

**Estimasi durasi:** pada batas atas 1000 video, jeda antar-video saja sudah ~8 detik × 1000 = **~2,2 jam**, ditambah jeda dan waktu request di dalam tiap video — total realistis satu batch penuh adalah hitungan jam (dijalankan semalaman), bukan menit. Ini trade-off yang diterima demi tetap zero-cost, dan alasan tambahan kenapa checkpoint/resume tidak bisa ditawar. Untuk jumlah video yang jauh di bawah 1000 (kasus normal menurut user), durasinya turun proporsional.

## Open Questions

Semua open question dari draf sebelumnya sudah dijawab user dan dipindah ke bagian "Decisions Locked In This Session" di bawah. Tidak ada open question tersisa yang blocking implementasi.

### Fase 3: Discovery by Username (KOL sentiment)

**Tujuan (dari user):** menilai sentimen masyarakat terhadap KOL yang dipakai brand. Alih-alih memasukkan ID video satu per satu, user memasukkan **username akun**, lalu sistem memilih sendiri video mana yang layak di-scrape komentarnya.

**Seleksi:** dari video yang diposting akun tersebut **dalam bulan yang diminta**, ambil **3 teratas dan 3 terbawah** berdasarkan view atau engagement. Rasionalnya: video terbaik dan terburuk memberi rentang sentimen paling informatif — yang paling disukai dan yang paling ditolak — sedangkan video di tengah cenderung mengulang pola yang sama.

**Kelayakan teknis: BISA, tapi wajib lewat Playwright.** Sudah dibuktikan lewat probe (Premis #3): `api/post/item_list/` dan `api/user/detail/` balikin 200 kosong, dan halaman profil polos hanya 1485 byte tanpa data video sama sekali. Tidak ada jalur `requests` polos ke daftar video sebuah akun. Karena Playwright memang sudah masuk rencana di Fase 2, ini tidak menambah dependency baru — hanya menaikkan perannya dari cadangan menjadi mesin utama jalur discovery.

**Alur:** username → Playwright buka profil, ambil daftar video bulan itu beserta metriknya → pilih top 3 / bottom 3 → keluarkan daftar ID video → **masuk ke pipeline Fase 1 yang sama** (pengambilan komentar via `requests`). Jadi Fase 3 adalah lapisan penghasil input di depan sistem yang sudah ada, bukan sistem terpisah.

**Belum diputuskan (perlu dibahas saat implementasi Fase 3, tidak memblokir Fase 1):**
- Metrik pemeringkat: view saja, atau engagement (like + komentar + share)? Keduanya terbaca dari profil, tapi menghasilkan urutan berbeda.
- Perilaku kalau akun memposting kurang dari 6 video di bulan itu (ambil semua, atau lewati?).
- Apakah satu CSV boleh mencampur baris berisi username dan baris berisi URL video, atau dipisah jadi dua file berbeda.

## Decisions Locked In This Session

**PIC & operator:** user sendiri (data analis), CLI terminal saja — tidak perlu UI/scheduler otomatis.

**Volume:** sampai 1000 video per bulan per batch — ini **batas atas, bukan target**. Jumlah nyata ditentukan isi CSV tiap bulan dan boleh jauh lebih sedikit.

**Delay anti-bot:** berlapis — 7-10 detik acak antar-video (usulan user), 1-3 detik acak antar-request di dalam satu video (lihat Kebijakan Delay).

**Fitur discovery by username (Fase 3):** disetujui secara konsep, wajib lewat Playwright, dikerjakan setelah Fase 1 terbukti jalan. Detail seleksi metrik dibahas saat implementasi.

**Cap komentar per video:** maksimal 200 komentar per video (termasuk reply dihitung total). Reply per komentar dibatasi maksimal 5 (semula 10, diturunkan setelah batch nyata pertama — lihat Temuan dari Data Nyata) (bukan mengikuti pagination penuh tanpa batas seperti kode lama `get_all_replies` yang loop sampai habis) — mencegah satu komentar viral dengan ribuan reply menghabiskan seluruh budget request untuk satu video, penting karena volume 1000 video/bulan membuat efisiensi per-video jadi kritis.

**Format Input Video:** daftar video per bulan dimasukkan lewat **file CSV**:
- Kolom video boleh bernama `url_or_id` **atau** `id_konten` (**salah satu wajib ada**). Export order-mirror milik user memakai `id_konten`, dan meminta rename kolom manual tiap bulan adalah langkah yang pasti terlupa suatu saat.
- `url_or_id` (**wajib**, atau `id_konten`) — URL TikTok atau ID video. Kosong atau tidak terbaca → baris di-skip dengan pesan jelas, bukan crash diam-diam.
- `account_type` (**opsional**, default `unknown`) — status akun yang memposting video: `affiliate`, `kol`, atau apa pun yang dipakai tim. Teks bebas, tidak divalidasi.

Keputusan `account_type` opsional diambil sadar: kehilangan satu video karena satu sel Excel terlewat lebih mahal daripada label yang perlu dirapikan belakangan. Label bisa diperbaiki di hasil tanpa scrape ulang.

Satu baris CSV tidak valid tidak menggagalkan seluruh batch — di-skip dan dicatat di ringkasan akhir run supaya kelihatan mana yang perlu diperbaiki di CSV berikutnya. Video yang mengembalikan nol komentar juga diberi peringatan, karena itu biasanya tanda ID salah.

**Failure Signature untuk Smoke Test:** dianggap **gagal** kalau salah satu dari ini terjadi saat scrape 1 video kecil (size=3):
- Response bukan JSON valid (halaman HTML block/captcha).
- HTTP status bukan 2xx.
- Response HTTP 200 dengan body kosong (tanda endpoint mulai mewajibkan signing).
- JSON valid tapi field `comments` kosong padahal video diketahui punya komentar.

**Dihapus dari daftar ini saat implementasi:** cek `caption`/`video_url` kosong. Diukur langsung pada 2026-08-28, blok `share_info` hanya muncul di **10 dari 16 request identik** ke video yang sama — TikTok memang mengembalikannya tidak konsisten. Menjadikannya sinyal kegagalan berarti batch berjam-jam bisa diblokir tanpa alasan nyata. Deteksi perubahan struktur dipindah ke parser komentar, yang melempar `SchemaError` kalau sebuah komentar tidak punya `cid` — sinyal yang stabil. Caption sendiri sekarang dipungut dari halaman mana pun yang membawanya (gratis, tanpa request tambahan) dan boleh kosong.

Kalau smoke test gagal: proses berhenti SEBELUM batch penuh jalan, exit code non-zero, pesan error singkat yang bisa langsung di-forward operator ke tim teknis (bukan stack trace mentah) — lalu barulah fallback Playwright (Fase 2) dicoba otomatis satu kali sebelum benar-benar berhenti.

## Success Criteria

- Bisa menjalankan satu perintah dengan daftar video (CSV), menghasilkan satu dataset bulanan (JSON + CSV) tanpa crash.
- Output ditulis sebagai **satu pasang file per bulan**: `runs/YYYY-MM/comments.json` dan `comments.csv`, dengan `account_type` sebagai kolom biasa. Tidak dipecah per tipe akun — pemfilteran dan pengelompokan tetap jadi wewenang analis, bukan dibakukan ke dalam struktur file. Kalau dijalankan ulang untuk bulan yang sama, file **ditimpa** (overwrite), bukan ditumpuk.
- Smoke test mendeteksi kalau API TikTok berubah/berhenti bekerja SEBELUM batch bulanan penuh dijalankan — definisi "gagal" mengikuti Failure Signature di bagian Open Questions (bukan gagal diam-diam).
- Tidak ada biaya berjalan (no paid API, no paid proxy).
- Output bisa langsung dipakai data analyst (format terstruktur) tanpa perlu tanya balik ke pembuat kode.

## Temuan dari Data Nyata (2026-08-28)

Batch pertama terhadap 11 video asli milik brand (export `mirror_orderan_aff_tiktok`) mengubah tiga keputusan. Semuanya tidak mungkin ditemukan lewat satu video sample.

**1. Smoke test satu video memblokir batch sehat.** Video pertama di CSV nyata (`7532149368489594117`) mengembalikan nol komentar. Smoke test lama menganggap itu tanda API rusak dan menolak menjalankan seluruh batch. Probe langsung ke 11 video: 9 punya komentar (sampai 1.574), 2 memang nol — respons 302 byte, JSON valid, `total: 0`, yaitu video yang komentarnya dimatikan atau dihapus. Jadi ~18% video normal-normal saja tidak punya komentar, dan peluang salah satunya ada di baris pertama itu tinggi.

Smoke test sekarang memeriksa sampai 5 video dan lolos pada video pertama yang berkomentar. Hanya jika semua probe kosong barulah run dihentikan.

**2. Balasan menelan jatah komentar utama.** Dari 1.497 baris hasil batch pertama: 905 balasan, hanya 592 komentar utama. Kasus paling ekstrem: video `7517948957125807416` punya 1.549 komentar di TikTok tetapi hanya menghasilkan **37 komentar utama** — 163 slot sisanya habis untuk balasan.

Untuk mengukur sentimen publik terhadap produk, komentar utama umumnya lebih bernilai daripada percakapan balas-balasan antar penonton. Default `--max-replies` diturunkan dari 10 menjadi **5**.

**3. Komentar kosong bukan komentar gambar.** Dugaan awal (komentar stiker/foto) **salah** dan sudah diverifikasi lewat probe langsung: komentar berteks kosong mengembalikan `image_list: None`, `status: 1`, `no_show: False`. Benar-benar kosong — nol teks, nol gambar, tidak ada yang bisa dibaca atau diskor.

Karena itu komentar berteks kosong sekarang **dibuang dan tidak memakan jatah cap**. Penyaringan dilakukan sebelum parsing, sehingga balasan milik komentar kosong bahkan tidak ikut ditarik — menghemat request. Komentar beremoji tetap disimpan: emoji adalah teks dan membawa sentimen. Flag `--keep-empty` mengembalikan perilaku lama.

Konsekuensi teknis yang perlu diingat: kursor halaman harus maju sebesar **jumlah komentar yang dikembalikan API**, bukan jumlah yang lolos saringan. Kalau tidak, halaman yang tersaring akan diminta ulang terus-menerus. Ini dijaga oleh tes `test_cursor_advances_by_the_unfiltered_page_size`.

**Catatan cap:** total per video bisa melebihi 200 sedikit (terlihat 201 dan 203). Ini disengaja — sebuah komentar tidak pernah dipisahkan dari balasannya hanya demi angka bulat. Kelebihan maksimal sebesar `--max-replies`.
